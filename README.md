# Vzihk — Практика №1: UDP-сервер и UDP-клиент

Дисциплина: «Проектирование и разработка многопользовательских игр и клиент-серверных систем».
Проект: **Vzihk**.

Реализовано на **C# / .NET** (проверено на .NET 8 и .NET 10 SDK — при желании поменяйте
`TargetFramework` в `.csproj`-файлах под установленную у вас версию), обмен данными —
через `System.Net.Sockets.UdpClient` (обёртка над Berkeley Sockets), без сторонних библиотек.

## Протокол обмена

Каждый пакет состоит из заголовка (7 байт) и полезной нагрузки переменной длины:

| Поле          | Размер   | Описание                                   |
|---------------|----------|---------------------------------------------|
| CommandType   | 1 байт   | тип команды (см. ниже)                      |
| Sequence      | 4 байта  | порядковый номер пакета (uint)              |
| DataSize      | 2 байта  | размер payload в байтах (ushort)            |
| Payload       | DataSize | данные, специфичные для типа команды        |

Типы команд (`CommandType`):

* `MOVEMENT (1)` — клиент → сервер. Payload: `float X, float Y` (8 байт) — запрошенная позиция игрока.
* `SHOOT (2)` — клиент → сервер. Payload: `float AngleDegrees` (4 байта) — угол выстрела.
* `StateUpdate (100)` — сервер → клиент, ответ на `MOVEMENT`. Payload: `float X, float Y` — актуальная позиция.
* `ShootResult (101)` — сервер → клиент, ответ на `SHOOT`. Payload: `byte Hit, ushort AmmoLeft`.
* `Error (255)` — сервер → клиент, если пакет не удалось разобрать (короткий заголовок, битые данные).

Сервер идентифицирует игроков по их `IPEndPoint` (IP + порт отправителя), так как UDP не
устанавливает соединение — этого достаточно для учебной задачи без авторизации.

## Топология сети

### Выбранная схема: клиент-сервер (звезда)

```
        Клиент A
            \
             \
Клиент B ── Сервер (порт 11000) ── Клиент C
             /
            /
        Клиент D
```

Каждый клиент обменивается пакетами только с сервером — клиенты никогда не общаются
друг с другом напрямую. Сервер — единственный источник истины (authoritative server):
он принимает решения о позициях игроков и результатах выстрелов, а не просто
пересылает данные между игроками.

### Почему выбрана именно эта топология, а не peer-to-peer (mesh)

* **Авторитетность и защита от читерства.** В mesh-топологии каждый клиент сам
  вычисляет часть игровой логики (например, попадания), и ему приходится доверять.
  В звезде решение всегда принимает сервер — клиент физически не может подделать
  результат выстрела или телепортироваться, отправив произвольные координаты
  (в текущей версии сервер пока принимает координаты как есть, но архитектура уже
  готова к добавлению валидации на сервере).
* **Сложность растёт линейно, а не квадратично.** При N игроках в звезде — N
  независимых соединений «клиент ↔ сервер». В полносвязной mesh-сети было бы
  N·(N-1)/2 соединений: при 4 игроках это всего 6, но уже при 10 — 45, а логика
  синхронизации состояния между всеми узлами становится сложной и по-настоящему
  неудобной без центрального арбитра.
* **NAT/файрвол.** В mesh каждому клиенту нужно быть доступным по входящему
  соединению от других клиентов (проблема NAT traversal, обычно требует STUN/TURN
  серверов). В звезде входящий порт нужен только серверу — клиенты лишь
  инициируют исходящие пакеты, что работает из любой домашней сети без
  дополнительной настройки.
* **Централизованный лог.** Требование задания — «сервер должен вести лог всех
  полученных команд» — естественно реализуется именно при звездообразной
  топологии: все команды и так проходят через одну точку.

### Почему UDP, а не TCP

* Игре важнее низкая задержка «здесь и сейчас», чем гарантия доставки каждого
  пакета: устаревшая позиция через секунду будет заменена новой, повторно
  досылать её незачем — а TCP как раз тратит время на переотправку и
  гарантированный порядок доставки.
* У UDP нет накладных расходов на установку соединения (3-way handshake) и на
  подтверждения каждого пакета — заголовок нашего протокола (7 байт) сопоставим
  по размеру со служебными данными самого UDP (8 байт) и заметно легче TCP.
* Для команд, которым всё же важна надёжность (например, будущая команда
  `HELLO`/регистрации), в протокол легко добавить свой ACK и повтор поверх UDP,
  не переходя на TCP целиком — это стандартный подход в сетевых играх.

### Расчёт нагрузки для 2-4 игроков

Целевая нагрузка задания небольшая, поэтому расчёт нагрузки в первую очередь
показывает, что архитектура имеет большой запас прочности:

| Параметр                                | Значение                                    |
|------------------------------------------|----------------------------------------------|
| Размер одного пакета (заголовок+payload) | 11–15 байт (без учёта заголовков UDP/IP)      |
| Служебные данные UDP + IP (IPv4)         | ~28 байт на пакет                             |
| Частота отправки на клиента               | 1 пакет/сек (по условию задания)              |
| Пакетов в секунду на клиента (туда+обратно) | 2 (запрос + ответ)                         |
| Игроков в комнате                        | 2–4                                           |
| Суммарный трафик сервера при 4 игроках    | ≈ 4 × 2 × 40 байт ≈ 320 байт/сек              |

Это исчезающе малая нагрузка даже для домашнего интернет-соединения — узкое
место в текущей реализации точно не пропускная способность сети. Сервер
обрабатывает каждый входящий пакет в отдельной асинхронной задаче
(`Task.Run`-подобная модель через `async`/`await`), поэтому обработка одного
клиента не блокирует приём от остальных — при 2-4 игроках сервер даже на
слабом железе не заметит нагрузки.

### Задержки (latency)

* Единственный источник задержки при 2-4 игроках в одной локальной сети —
  сетевой RTT (round-trip time), обычно единицы миллисекунд в Wi-Fi/LAN и
  10–50 мс в интернете между разными городами; обработка на сервере занимает
  микросекунды и на фоне сети не заметна.
* У клиента установлен таймаут ожидания ответа 2000 мс (`ReceiveTimeoutMs`) —
  если пакет (запрос или ответ) потерялся в сети, клиент не «зависает», а
  сообщает о таймауте и продолжает работу на следующем тике.
* Периодичность отправки (раз в секунду) выбрана исходя из задания и годится
  для пошагового прототипа; для более отзывчивого геймплея (полноценного
  реального времени) частоту тика обычно поднимают до 10-30 раз/сек — этот
  протокол такое увеличение выдержит без изменений в архитектуре, так как
  нагрузка (см. таблицу выше) масштабируется линейно и всё ещё останется
  небольшой при 2-4 игроках.

### Ограничения текущей топологии и куда расти дальше

* Сервер пока не транслирует состояние одного игрока остальным (нет
  broadcast) — каждый клиент видит только собственный ответ. Для реальной
  игры на 2-4 игрока это следующий обязательный шаг: сервер должен рассылать
  обновлённое состояние всех игроков всем подключённым клиентам.
* Игроки идентифицируются по `IPEndPoint` без явной регистрации — при смене
  сети/порта клиента (например, реконнект) сервер создаст «нового» игрока.
  Для стабильной работы с несколькими постоянными игроками нужен явный
  `HELLO` с игровым ID.
* Пропускная способность и задержки посчитаны для локальной сети/студенческого
  прототипа на 2-4 игроков; для публичного сервера с десятками одновременных
  игроков потребуется отдельный пул потоков на приём, батчинг обновлений и,
  возможно, переход на надёжный UDP-протокол поверх текущего (свои ACK и окно
  подтверждений, как в разделе «Что можно расширить»).

## Сборка и запуск

Требуется .NET SDK 8.0+ (в разделе `TargetFramework` каждого `.csproj` укажите версию,
установленную на вашей машине — например, `net10.0`, если стоит .NET 10 SDK).

```bash
cd Vzihk-lab1
dotnet build
```

Запуск сервера (в одном терминале, порт по умолчанию — 11000):

```bash
dotnet run --project Server -- 11000
```

Запуск клиента (в другом терминале; можно запустить несколько клиентов одновременно):

```bash
dotnet run --project Client -- 127.0.0.1 11000
```

Клиент раз в секунду отправляет команду (чередуя `MOVEMENT` и `SHOOT`), выводит в консоль
что отправил и что получил в ответ. Сервер логирует каждую полученную команду в консоль
и в файл `server.log` (создаётся рядом с исполняемым файлом сервера).

## Что можно расширить в следующих практиках

Текущая реализация — это "запрос-ответ": клиент шлёт команду, сервер отвечает
только ему. Она не может передать никакой информации от одного игрока другому.
Чтобы игроки реально видели и влияли друг на друга, сервер должен научиться
**рассылать (broadcast)** пакеты не только отправителю, но и остальным
подключённым `IPEndPoint` — это ключевое изменение, без которого пункты ниже
не имеют смысла (кроме первого — он и есть это изменение).

### Фичи взаимодействия между клиентами

1. **Синхронизация позиций между игроками (broadcast state).** Сейчас сервер
   отвечает `StateUpdate` только тому, кто прислал `MOVEMENT`. Нужно, чтобы
   после каждого обновления сервер рассылал позиции всех игроков всем
   подключённым клиентам — иначе игроки друг друга физически не видят.
   Лог: `BROADCAST -> позиция игрока id=1 разослана 3 получателям`.

2. **Попадание по конкретному игроку, а не случайное число.** `SHOOT` должен
   указывать не только угол, но и проверяться сервером против реальных
   координат других игроков (raycast/дистанция), с явным указанием, в кого
   попали. Лог: `SHOOT -> игрок id=1 попал в игрока id=2 (дистанция 4.3)`.

3. **Список игроков в сессии (`LOBBY`/`PLAYER_LIST`).** Команда, которой клиент
   запрашивает у сервера, кто ещё сейчас в игре (id, ник, позиция), чтобы
   отрисовать их у себя.
   Лог: `PLAYER_LIST -> отправлен игроку id=3 (в сессии: id=1, id=2, id=3)`.

4. **Игровой чат между игроками.** Клиент шлёт текст, сервер рассылает его
   остальным подключённым клиентам.
   Лог: `CHAT -> id=1 → всем: "прикрой слева"`.

5. **Команды/альянсы (`TEAM_JOIN`).** Игрок выбирает команду (например,
   красные/синие), сервер следит, чтобы `SHOOT` не наносил урон союзникам
   (friendly fire off).
   Лог: `TEAM_JOIN -> игрок id=2 вступил в команду "Синие"`.

6. **Взаимодействие через игровые объекты (например, захват флага).** Один
   игрок подбирает объект, остальные видят, у кого он сейчас, и могут его
   выбить.
   Лог: `FLAG_CAPTURED -> флаг подобран игроком id=1`,
   `FLAG_DROPPED -> игрок id=1 уронил флаг (убит игроком id=2) в точке (2.1, 5.0)`.

7. **Столкновения между игроками (`COLLISION`).** Сервер проверяет, не пытается
   ли игрок переместиться в точку, где уже стоит другой игрок, и
   корректирует/отклоняет движение.
   Лог: `MOVEMENT -> отклонено: столкновение id=1 с id=3 в (1.0, 1.0)`.

8. **Спектейт/наблюдение за другим игроком (`SPECTATE`).** После смерти или по
   запросу клиент может подписаться на трансляцию состояния конкретного
   другого игрока.
   Лог: `SPECTATE -> игрок id=2 наблюдает за игроком id=1`.

9. **Эмоции/пинги на карте (`MARKER`/`EMOTE`).** Быстрое взаимодействие без
   чата: игрок ставит метку "сюда!" или эмодзи, сервер рассылает остальным.
   Лог: `MARKER -> игрок id=1 поставил метку "Опасность" в (3.0, 4.0), разослано 2 игрокам`.

### Прочие технические улучшения

* Настоящая проверка попадания по позициям других игроков (сейчас `SHOOT` — случайный 50/50) — см. пункт 2 выше.
* Явный `HELLO`/`DISCONNECT` для регистрации и выхода игроков вместо неявного создания по первому пакету.
* Защита от потери и дублирования пакетов (ACK с повторной отправкой, окно последовательности).
* `HEARTBEAT` — периодический пустой пакет от клиента; если сервер не получает его дольше таймаута, считает игрока отключившимся и удаляет из сессии.
* `PING` — клиент шлёт метку времени, сервер отражает её обратно, замеряется RTT (пригодится для демонстрации задержек, см. раздел «Топология сети» выше).
* `HEALTH`/`RESPAWN`/`SCORE_UPDATE` — полноценная система здоровья, смерти/возрождения и таблицы очков поверх попаданий из пункта 2.
* Сериализация состояния всех игроков и broadcast всем подключённым клиентам — см. пункт 1 выше, это базовый механизм, на котором строятся все остальные фичи взаимодействия.
